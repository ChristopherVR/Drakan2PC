# Issue 1: host departure leaves the other player in the level

## Evidence and correction

Two distinct lifecycle gaps existed. The input glue recognized the confirmed native Quit box transition (screen 1 to title screen 8), but modern Quit to Title only suppressed process exit. It never left the network session. A listen server therefore continued servicing the other player while its owner sat at the title. Confirmed manual returns now enqueue Leave. Opening pause, opening confirmation, and cancelling it do not leave. Automated results returns deliberately retain the session so the lobby/rematch flow still works.

Separately, an established client receiving DisconnectedEvent set an error but never left its loaded native world. It now requests the existing native return-to-title sequence. Initial rejection or connection timeout stays in the joining menu. Established loss, including a kick or transport timeout, returns to title; a rejected kick keeps the server rejection text. Legacy sessions stop reconnecting after established-session loss. The retry gate also excludes the frame processing an established disconnect, before its event is drained.

The existing same-tick disconnected snapshot disables Playing, clears remote snapshots, and clears the co-op connection flag. The failed session remains available to the title multiplayer screen so its existing rejection transition displays the reason and issues Leave. Normal session teardown then clears redirects, pending launches, co-op queues/link and increments the session serial. The EE thread removes absent remote ghosts. This preserves error handling instead of silently resetting the UI to Offline. A dedicated server player departure remains PlayerLeave; it does not terminate other clients merely because the departing player was its longest-connected lobby leader.

## Validation and limits

Added `netplay_policy` assertions around the actual production decision seam: confirmed manual quit versus cancel/open-pause, and automated results/loss returns preserving the lobby/error. Extended `net_match` with longest-connected player departure while another dedicated-server client remains connected and can send state. Extended `net_udp_smoke` with actual UDP listen transport destruction: the connected client receives one non-rejected disconnect and cannot send match state afterward.

The parent integration task runs the shared canonical builds/tests. This investigation did not launch another game or independently build a shared tree. Live two-instance confirmation of manual host Quit to Title, client title/error presentation, repeated join after cleanup, and abrupt process loss is still required. UDP graceful teardown sends a disconnect datagram; abrupt termination or a lost datagram uses the existing 10-second receive timeout. Native title automation has its existing 45-second fallback and requires the game to service input/menu ticks.

The first valid modern-menu two-instance run used canonical deployed executable SHA-256 `F75B99238530B474C8503B61E15A33D553BC501850AE4A191084E13C4D8D9ECB`, launched twice directly from `dist/DrakanPC`, with independent settings, cards, logs, screenshots and recipes under `build/harness/issue1-host-disconnect-modern`. Both clients reached Playing. The host executed the actual modern Quit to Title action, native box Yes and screen 1 to 8 transition at input t=108.739; the guest received DisconnectedEvent and automatically performed START, Quit to Title, box Yes and reached title at input t=110.097 (39 automation frames). Both processes later exited with code 0. Screenshots confirmed the title replaced the playable level.

This exposed a second integration gap in error acknowledgment: title initialization only resumed connected result/lobby sessions. A rejected retained session therefore reached the main title without executing the lobby rejection/Leave transition. Title initialization now also resumes rejected sessions that still have `inSession=true`. The existing multiplayer screen transitions to Join/Host and issues Leave. After actual teardown the net thread retains only Rejected and its message in a fresh offline State; this keeps the reason readable rather than erasing it a frame later. No roster, phase, hosting flag or `inSession` survives cleanup. Host/Join already replace State before queuing a new session and the atomic session gate has been cleared. Repeated Leave outside a session is dropped. The title resume policy requires `inSession`, so the retained offline error cannot trigger another resume loop.

The initial preparation attempt omitted modern title mode and navigated the native Controls page; it established no network session and was closed cleanly. It is excluded from acceptance. A redundant pre-fix focused run was closed cleanly at the lobby once source review established the missing rejected-session resume. Final post-rebuild evidence is recorded below when available.

Two follow-up runs on deployed SHA-256 `8F86076BFFC2084CDD41D9856155A05ECA4DDD842508A08762F3D03611C230B6` reproduced an additional stall immediately after the title boundary, before the title overlay resumed its multiplayer page. ## Final live acceptance

After the ghost-lifetime correction, deployed SHA-256 `C2ED9A75BABF249422B7C594ED6FEAB14FCF783CEA51AA3AF1512F449C8DED27` passed the same bounded reproduction. Evidence is under `build/harness/issue1-host-disconnect-lifetime`, with machine-readable checks in `summary.json`. Both instances reached Playing. The host manually confirmed Quit to Title (input t=110.83), and the guest received disconnect, completed the native automatic title transition in 39 frames, and resumed the multiplayer rejection path. Visually inspected `b/client_loss_error.png` shows Join Game with the readable persistent reason “Connection to the server lost”. The subsequent actual menu Host/Begin action succeeded: the former guest became player 1 of its own new listen server at netplay t=130.707, and `b/client_rehost_lobby.png` shows its one-player host lobby. This demonstrates that the previous session gate, socket and launch state were released sufficiently to create a new session. `b/client_playing.png` visibly contains native Rynn, but the selected character was actually Sevoth (`177d`). Repeated local-character visible/binding logs indicate recreation each frame. Therefore this run exposed a selected-character rendering regression in the lifetime correction; avatar equivalence is not accepted even though host departure/error/rehost succeeded.

Both scripts completed and both processes exited 0 with ordinary renderer shutdown, no guest-boundary stall and no game-thread shutdown timeout. No binaries or DLLs were copied into private play folders: both launches used the same canonical dist executable and isolated settings/cards/output. The capture helper was prepared but not needed because this final run did not stall. This is a successful single controlled acceptance after the lifetime correction, not a broad multiplayer stability soak or a live abrupt-process-loss/timeout test. Dedicated-server player departure and UDP destructor disconnect remain covered by the focused transport tests.
