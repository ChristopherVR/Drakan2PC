# Orb edge lines: captured atlas and point-sampling evidence

Investigated on shared source baseline `edd4fff`, with existing combined-game
screenshots identifying executable `54F082`. This worker ran CPU analysis only;
no game, GPU, WARP, deployment, patch export or push. Main owns the sky and
temporal investigation. No renderer correction is claimed here.

The subsequent [source-only sampling follow-up](sprite-sampling-convention.md)
establishes integer native GS pixel centres and identifies a discrepancy in
our native raster mapping. It supersedes the unresolved native-convention
question below; scale4 policy and renderer before/after validation remain open.

## Concrete pixel source

The straight white orb edges have an identified source in the submitted HUD
highlight sprites and the uploaded atlas. They are not separate line primitives
in the inspected recording. This establishes their content/sampling origin;
it does **not** establish that the border was intended to be visible in the UI,
or that removing it would correct GS behavior.

Private capture:
`tools/graphics-followup/build/graphics-orb/captures/gscap_20261017_222753.bin`.
The CPU parser sees 87,701 vertex kicks: 1,920 sprite vertices, 82,272 triangle
strip vertices, and 3,509 triangle fan vertices. No point, line-list or line-strip
primitive vertices occur. This does not exclude thin geometry made of triangles.

Two complete CT32 host uploads target TBP15008/TBW2, origin(0,0), size128x128:
after kicks38046 and81903, in capture-relative frames0 and2. Each contains
65,536 bytes with SHA256
`C891E7A6FA92A5790BDDD4B6C892356C746F8639D701CCC29B60ECB864AE8956`.
Both uploads are byte-identical to the original disc's
`ENGLISH/COMMON/INTERFCE/INTERFCE.TXD`, type0x40/id128/sub0, decoded RGBA.
The renderer content hash is `0aca2ff6ae460ac2`; direct byte equality against
the disc, rather than that hash alone, was checked. The TXD resource has
128x128 pixels, bpp32, flags7 and a 64-byte header.

The atlas's highlight rectangle has an opaque-looking white perimeter at
x27/88, y2/61, inclusive. Every perimeter texel is RGBA(255,255,255,127), in
GS alpha units. It surrounds the soft curved highlight and is already present
in the disc asset. It was not generated by SR, NR, texture upscaling, the cache
coherence fix, or a runtime debug-line draw.

## Submitted draws and sample footprint

All these sprites use TEX0 `0x00075405dc00baa0`, TEST `0x3002d`, ALPHA `0x44`,
CLAMP `0x5`, and TEX1 `0xfffffed000000000`. Both GS magnification and
minification filters select point sampling. They use STQ with Q=1, TCC=1,
TFX=MODULATE, vertex RGBA(127,127,127,128).

The red fill is a different region of the same atlas: UV(28.5,127.5) to
(88.5,67.5), kicks40540..40541 for Equipment. The ring uses a separate indexed
texture. The earlier shifted-RT-row correction is not another explanation
for the white perimeter in the original uploaded pixels.

`gs_shaders.h::sampleLvl` floors interpolated coordinates for point sampling.
For an untransformed 60x58 highlight at raster scale4, pixel-centre
interpolation visits u28.625..88.375 and v60.375..2.625. Therefore it samples
two physical columns at x88 and two physical rows at y2. The other two border
edges, x27 and y61, are not sampled. A synthetic atlas containing only that
perimeter produces exactly the observed orientation of the L:940 border
samples in the240x232 rectangle, accounting for its shared corner.

This is a CPU characterization of the **current shader math**, not a GS
reference renderer or actual D3D11 pixel regression. At scale1 the same model
still samples x88 in its last column, while its last row uses y3. HUD aspect,
HUD size and final-window filtering alter the physical footprint. A generic
"upscaling-only" diagnosis would be too strong.
The model uses original 1x atlas texels; it does not reproduce asynchronous
xBRZ/HD replacement contents or the historical faulty RT alias path. The
original atlas border and the final screenshots remain direct observations.

An illustrative UV shift(-0.5,+0.5) avoids the perimeter in the synthetic model.
It also changes the highlight footprint. Its success does not establish the
correct GS pixel-centre convention, validate all other HUD sprites, or justify
a general sampler change. No such change was applied. An asset-specific border
removal would likewise be a deliberate visual workaround until the intended
appearance is established.

## Existing final images

Read-only crops from native2500 show the straight bottom line beneath the
health artwork and the bottom/right L beside the mana artwork. A simple RGB
probe at x560..599/y2082..2083 finds all40 pixels on each row with all channels
at least220 in each final Equipment2500, Journal4000 and Bow4500 image, in
both native and SR/NR modes. This is a measured straight-border segment, not
an entire-image comparison or a matched-pose renderer regression. Gameplay1900
also visibly has the L, with different HUD size and placement.

The screenshots and model support an atlas-footprint explanation. They do not
independently establish original-console parity or the UI artist's intent.

Before changing renderer sampling, establish the expected original highlight
footprint using a reference GS/console image or an independently supported

corresponding synthetic GIF pixel regression, and run before/after WARP only
after an explicit GPU handoff. A private standalone fixture can seed this
atlas directly; replaying the whole late recording without initial VRAM is
unnecessary and would not be a faithful scene replay. Native/SR game image
validation remains a separate final step.

## Smoke remains unvalidated

The existing hostile675 combat views show a torch flame; previous receipts do
not establish a controlled smoke plume. Existing fixture documentation covers
starting-region saves, with no demonstrated dragon breath or mounted Arokh
sequence. The 816-resource original save has no literal "smoke" string after
decompressing its records; that is not proof that it contains no smoke emitter.
Executable strings such as "Smoke Generator", "Rising Smoke" and "Particle
Smoke" are resource/type leads, not identified active draws or repeatable
effects. Historical files named `smoke_a` refer to smoke testing, not evidence
of smoke particles.

No reproducible smoke effect was established within this bounded CPU review.
The next smoke run needs an identified active emitter/trigger in an existing
save, a fixed camera and timed recipe that visibly yields a plume, and a short
GIF/texture/draw capture covering its production and sampling. A torch alone
must first be checked for actual smoke emission. Successful spell-projectile
or flame rendering does not validate smoke blending. Game/GPU time must be
coordinated after the current reservations.
